# Lua 5.1 binary decoding and verification validation

The engine now recognizes the leading escape byte and incrementally decodes
native Lua 5.1 chunk headers, flat prototype trees, constants, nested functions
and debug metadata. It retains its cursor and pending field lengths across
reader calls. Strings are copied once when complete; input prefixes and
prototype headers are not reparsed. Declared counts do not trigger reservations
for unavailable data. Checked offsets and a 200-level native nesting limit bound
structural work/storage by supplied input and active nesting.

The verifier checks all 38 native opcodes, registers, constants, global names,
captures, closure bindings, conditional skips, jumps, open results, varargs and
SETLIST payloads. A linear payload-discovery pass handles raw count words even
when they resemble opcodes. Native ABI header mismatches are rejected; the
verified runtime profile is Windows x86-64 MSVC, size_t 8, int/instruction 4,
binary64 8, little endian and nonintegral Lua numbers. The decoder uses its
target-native profile, but other platform runtime validation remains open.

This is a structural checker, not a proof that all C-accepted chunks are safe
to execute. Noncanonical boolean/test flags and reversed nil ranges are rejected
more strictly than the PUC checker; a null string constant is also rejected.
These adversarial cases are outside the matching-reference claims. The eventual
instruction bridge must verify the generated engine IR before execution.

Fixed buffers, `loadstring`, reader-based `load`, `loadfile` and `dofile` share
this validation. Reader errors retain arbitrary values under protected calls;
the first reader probe fixes text/binary selection, including an empty first
result. Named files reopen in binary mode before validation, avoiding text-mode
CRLF/control-Z translation. An executable header is handled like the native
loader, including searching for the first escape byte after reopening. Native
diagnostic names retain their complete bytes and do not gain a source line.

All **375 tests** pass: 344 integration groups, thirty unit groups and one
documentation example. Six new unit groups cover:

| Area | Evidence |
| --- | --- |
| Official dumps | Byte round trips, every split point and one-byte feeding over closures, captures, loops, constants and arithmetic. Stripped wire forms are built explicitly because the Lua 5.1 C dump API has no strip argument. |
| Truncation/header | Every nonempty proper prefix of a native dump and all eleven non-dispatch header-byte corruptions match reference rejection categories. |
| Instructions | Every bit of each word in a representative chunk is mutated and checked in Rust; malformed chunks are never executed by the C oracle. |
| Resource declarations | size_t maximum strings and int maximum code counts fail without reserving the declared storage; a 201-prototype chain reaches the depth error without recursive decoding. |
| Generated bytes | 2,048 deterministic byte sequences, bounded storage and trailing-byte handling; the reference executes an unchanged valid chunk with a suffix. |
| Opcode/payload coverage | Official dumps cover all 38 native opcodes, captured-scope closure binding and a 25,551-element constructor requiring an extended SETLIST count. |

Three new differential integration groups check malformed headers/names,
one-to-four-byte reader calls with exact stopping counts and protected error
identity, plus named-file reopening with CRLF/control-Z and executable headers.
Existing text readers, files, resource limits, hooks, coroutines, GC and locale
regressions remain green. Formatting, strict crate Clippy with dependencies
excluded, whitespace checks and the normal/build dependency tree pass. The
latter contains only `deadlib-lua`; no Cargo dependency or unsafe code is added.
Production consumers remain on the legacy crate.

All [129 process probes](2026-10-25-rust-lua-chunk-codec-process.json) match full exit status,
stdout/stderr bytes and recorded file contents across official Lua 5.1.5, Rust
runner and CLI. Three additions cover header diagnostics, reader stop/error
behavior and binary file reopening. They use invalid input with defined native
rejections; no valid binary execution is counted as a matching Rust success.

The [official report](2026-10-25-rust-lua-chunk-codec-suite.json) retains sixteen unchanged,
checksum-pinned files, `_U=true`, 100-million-instruction limits and sixty-second
file deadlines. Rust still passes fourteen; the reference fifteen. Rust stops
at `calls.lua:243` for binary dumps. Both engines fail `files.lua:59`, the Windows
open-input rename assertion. The suite command remains unsuccessful; these are
isolated files, not complete `all.lua` or internal C API coverage.

All report hashes match the final tree. [Measurements](../performance/2026-10-25-rust-lua-chunk-codec.md)
retain two runs for 54 runtime and twenty-two frontend workloads. They measure
invalid-header rejection, not full decoding or execution throughput.

Valid native chunks deliberately return `Unsupported` after validation. The
round-trip encoder exists only in tests; it is not `string.dump`. Native-to-engine
instruction translation, root upvalue initialization, native debug/source mapping
and dump emission remain required. Persistent caching, native modules, broader
resource/platform/diagnostic work, Lua 5.2-5.5, optional JIT and integrations are
also unfinished. The full standalone-engine objective remains open.
