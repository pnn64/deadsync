Replace DeadSync’s production use of deadlib-lua-legacy with the independent deadlib-lua Rust engine.
Finish line: a normal DeadSync build uses deadlib-lua for all existing Lua execution, including song compilation, live song callbacks, noteskin preparation and Simply Love’s step_stats_gifs loader. Existing supported content and application behavior remain working.

This request explicitly authorizes integration and supersedes the older “integration deferred” instructions in the Lua documentation. The interpreter and C API removal milestones remain completed; do not reopen their entire scope.

Architecture:
- deadlib-lua owns the generic Rust parser/compiler, VM, GC, standard library and host API.
- deadsync-song-lua owns song, actor, command, timing and playback bindings.
- deadsync-noteskin owns noteskin bindings and preparation.
- Other existing Lua consumers use the same shared engine.
- Keep DeadSync-specific behavior out of deadlib-lua.

Establish the migration baseline:
1. Inventory every production dependency on mlua/deadlib-lua-legacy, including raw C API calls, retained Lua handles and downstream consumers.
2. Record the existing supported behavior, fixtures, regression commands and representative performance workloads before changing backends.
3. Use that inventory as the fixed acceptance scope. Additional StepMania features and unrelated interpreter improvements are separate work.

Implement the migration:
- Reuse and complete the existing rust-engine adapters.
- Migrate the full production song path: actor construction and methods, command lifecycle, managers, timing/RNG, input/messages, media, compiled output and live callbacks wherever currently supported.
- Migrate noteskin preparation and its supported callbacks, plus remaining production consumers such as step_stats_gifs.
- Preserve callback ordering, shared state, error handling, file/module behavior, sandbox restrictions and existing execution/memory limits.
- Replace legacy registry handles and raw C stack access with correctly rooted Rust host API values. Preserve object lifetime, cleanup, callback reentry and thread ownership.
- Add generic Rust embedding facilities to deadlib-lua only where the migration requires them. Do not recreate the entire mlua API or restore Lua C API compatibility.
- Preserve existing preparation/baking, live execution and fallback semantics. Any fallback must use deadlib-lua.
- Preserve cache correctness; version or invalidate incompatible artifacts rather than silently reusing them.

Cut over:
- Make deadlib-lua the unconditional production engine.
- Remove production legacy dependencies, backend switches and duplicate legacy implementations after their replacements are verified.
- Retain legacy only in explicitly isolated development/test oracle dependencies where useful. It must not enter the application’s normal or build dependency graph.
- Update manifests, profiles, tooling and active documentation. Preserve unrelated uncommitted work and historical reports.

Validate:
- Run relevant interpreter, adapter and downstream regression suites against the final source.
- Compare existing song fixtures, bundled/regression noteskins and GIF definitions against the recorded baseline.
- Exercise both preparation and live playback, including retained callbacks across GC and session teardown.
- Build the normal application and smoke-test song loading, gameplay and noteskin rendering. Compilation alone is insufficient.
- Verify the application dependency graph and build/link evidence contain no legacy Lua runtime.
- Run applicable formatting and Clippy checks. Report unavailable platform or interactive validation explicitly.
- Measure representative preparation time, live execution cost and memory before/after; report results without introducing a LuaJIT performance target.

Completion requires:
1. Every inventoried production Lua consumer uses deadlib-lua.
2. Existing supported behavior passes its applicable regression checks, with no unexplained new failures.
3. Normal application builds require no experimental engine flag and have no legacy runtime dependency or fallback.
4. Documentation accurately describes the production architecture and validation.

Do not delete, weaken or skip failing coverage to claim completion. Fix engine or adapter defects that block this migration. Record unrelated pre-existing defects separately.

New scene-baking capabilities, JIT/native-code backends, assembly optimization, broader language parity and exhaustive allocation-failure campaigns are outside this goal. Stop when the migration criteria are met.
