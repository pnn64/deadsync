# Lua token, judgment, and perframe work - 0.5.1175

Parent: `f2d8fea821cefb4aa7655302b8e4da2430ca16ff` (`0.5.1174`).
This pass follows `rust-performance.md`: measure hot paths (M-HOTPATH), reuse
allocations (M-MEM-REUSE), reserve known capacity (M-INITIAL-CAPACITY), and avoid
repeated work (M-THROUGHPUT).

## Three changes

1. **Normalize mod names without a temporary owned string.** The token
   application core used by `PlayerOptions:FromString` borrows already normalized
   ASCII names. Other short names use 64 bytes of inline storage, filtering
   nonalphanumeric characters and lowercasing ASCII exactly as before. Longer
   normalized names spill to the heap. Lua state/speed writes, boolean rules,
   modifier precedence, and partial-error behavior are unchanged. The public
   owned-string normalizer retains its original signature and implementation.
2. **Keep at most two judgment offsets inline.** Judgment scans consume a fixed
   pair of optional offsets instead of allocating a Vec per scalar/record. A
   record is matched before numeric conversion, avoiding a needless Lua table
   clone. In this mlua build the first clone of a unique reference promotes it
   to a heap-allocated shared counter. Eliminating that clone removes additional
   per-record churn. Numeric conversion, raw table lookup, hold-offset truthiness,
   offset order, sequence holes, and judgment thresholds are preserved.
3. **Stream perframe sample segments through two reusable snapshots.** The
   compiler previously retained sample beats, player states, and one actor-state
   Vec per sample, then emitted segments after the entire window. It now emits
   each segment once its next snapshot is available. Two snapshot Vecs retain
   capacity across windows, and sample timing is generated by an iterator.
   Scratch for this part changes from proportional to samples times actors to
   proportional to actors. Final output can still grow with the sample count.
   Callback/replay order, adjacent-state interpolation, final static tails,
   gaps, side-effect detection, and error propagation remain unchanged. Public
   Vec-returning sample and target helpers remain available.

No dependencies or production unsafe code were added. These changes concern
song-Lua evaluation/compilation, not the gameplay frame loop. Rolling snapshots
retain their high-water capacity only until compilation ends; outputs and other
compiler storage still allocate. Short mod normalization adds a 64-byte inline
payload plus SmallVec metadata to the stack.

## Benchmark method

Windows x86-64, Intel Xeon E5-2696 v4 @ 2.20 GHz, Rust 1.98.0
(`88d9e12ae`, LLVM 22.1.8), release optimization level 3 with full LTO.
The existing benchmark helper takes seven timing samples after three warmups,
then measures allocation churn in a separate operation. Three isolated serial
executable runs alternate old/new order: old first, new first, old first.
No Cargo compiler runs during measurement. Tables aggregate the median of the
three per-run medians. All 25 paired scenarios, including controls, are reported.

Windows `QueryThreadCycleTime` counts calling-thread CPU cycles, not retired
instructions. Thread-local allocator counters include allocations routed through
Rust's allocator, including Lua allocations in this mlua 0.12.1 / vendored Lua
5.4 build. Other threads or allocations bypassing Rust's allocator are outside
the counters. Requested/freed bytes are cumulative, not peak live memory or RSS.
Lua fixtures and handles are warmed and garbage collection is stopped for these
isolated scans; fixture construction and Lua teardown are outside timing.

Ownership boundaries and units:

- `mod_keys_*`: 16 scans of each input set per operation. Old normalization
  constructs/drops a String; the new caller consumes a borrowed normalized key
  inside its callback. Both results reach black_box. The public String-returning
  API is unchanged and is not the optimized path. Timing samples use 512
  operations; throughput counts keys.
- `mod_apply_*`: 16 calls to the token application core per operation, including
  parsing and Lua state/speed writes to warmed tables. Time samples use 128
  operations; throughput counts comma-separated tokens, including empty tokens
  in the control. Lua method dispatch and the outer FromString wrapper's owned
  input-string conversion are excluded. Zero churn here does not mean a whole
  Lua FromString call has zero allocations.
- `judgment_N_mode_M`: one complete judgment scan, including Lua sequence/raw
  reads, conversions, temporary ownership, and reduction. Modes are scalar
  (0), one-offset record (1), two-offset record (2), and invalid boolean (3).
  Time samples use 128 scans; throughput counts rows, or calls for empty input.
- `perframe_N_dynamic_D_len_L`: full `compile_perframes` plus reset of existing
  fixture state before each call, including entry extraction, sampling, state
  reads, target construction, and output destruction. Both versions start each
  compilation with fresh compiler scratch. Lua setup, input callbacks, context,
  and actor tables are outside timing. Results and actor/player handles reach
  black_box; old/new outputs are compared before timing. Eight compilations
  per timing sample; throughput counts sample ticks (calls for no entries).
  The fixtures include two tracked player tables. Dynamic cases write actor
  x/y and player x; static cases preserve their values. Messages are covered
  by regression tests but absent from these timing fixtures.

Every pair checks equivalent results before timing. Timing includes construction
and destruction of the temporary Rust storage being removed. Empty controls
are dominated by fixed call/measurement costs. No whole-song load-time, gameplay
FPS, hardware-cache-miss, or peak-RSS improvement is claimed.

Reproduce:

```powershell
cargo test -p deadsync-song-lua --lib lua_stream --locked
cargo test -p deadsync-song-lua --lib --release --locked
# Use Cargo's printed release test executable. Run three times, setting
# DEADSYNC_PERF_REVERSE=1 only for the middle run.
& <release-test-executable> lua_stream_bench --ignored --test-threads=1 --nocapture
```

## Measured effects

- `mod_apply_mixed`: **9.57% fewer cycles**; 42.691 -> 38.598 us/op. Allocation calls 64 -> 0; requested bytes 512 -> 0.
- `judgment_1024_mode_2`: **37.19% fewer cycles**; 368.459 -> 231.352 us/op. Allocation calls 2,048 -> 0; requested bytes 32,768 -> 0.
- `perframe_64_dynamic_false_len_1`: **4.52% fewer cycles**; 58,426.900 -> 55,789.938 us/op. Allocation calls 6,992 -> 6,893; requested bytes 3,669,592 -> 550,840.

The 64-actor perframe case requests **84.99% fewer bytes**. The longer
four-actor static case requests **87.73% fewer bytes**, with a 1.43% cycle
reduction. These are cumulative allocation savings, not measured peak RSS.

All allocator counters are identical across the three runs. Long mod names
still allocate, while numeric scalar/record judgment scans and common warmed
token application have no allocation churn. Common Lua temporaries remain
uncollected while garbage collection is stopped, so allocation and free counts
need not balance; both versions have the same net unfreed bytes in each case.

Tradeoffs: the zero-overlay one-beat perframe case takes 2.72% more cycles
while requesting 81.05% fewer bytes; the four-actor dynamic one-beat case
takes 3.73% more cycles while requesting 14.14% fewer bytes. Empty mod-token
batches take 33.31% more cycles (0.875 -> 1.167 us per 64 empty tokens, about
4.57 ns extra per token). These controls are retained in the report; this
pass does not improve CPU throughput in every workload.
