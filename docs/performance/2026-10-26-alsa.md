# ALSA ownership, enumeration, and timing measurements

Three optimizations are retained in `deadlib-audio-backend-alsa`:

1. Normalize the owned PCM ID in place. Shared aliases and exclusive hardware IDs
   keep their allocation; converting `plughw:` to `hw:` removes its prefix in
   place. This removes three forwarding/string-copy helpers.
2. Build output devices during enumeration. Remove `PhysicalOutputDevice`, its
   intermediate vector, eight card-name clones and eight temporary device-name
   strings in the eight-device fixture. Device order, names, capabilities,
   default selection and probe-error defaults remain the same. Probing now
   happens while each card's control handle is open.
3. Compute fallback delay nanoseconds only when `pcm.status()` fails. Keep the
   preceding `pcm.delay()` call and all subsequent ALSA calls in their original
   order. Successful status queries discard that delay value, so its integer
   division served no purpose. Status failures retain the original conversion.

The production section shrinks by 32 lines, including four helper functions and
one intermediate struct. No production unsafe code, dependencies, reciprocal
arithmetic or sample-rate special cases are added.

## Measurements

Debian WSL2, Intel Xeon E5-2696 v4, Rust 1.99.1 / LLVM 23.1.1, libasound
1.2.16.1. Actual Cargo release test binaries use the workspace release profile
(opt-level 3, LTO, default target CPU). Seven runs per variant alternate execution
order on CPU 0. Tables show medians; throughput is before cycles / after cycles.

| Operation | Before cycles/op | After cycles/op | CPU throughput |
| --- | ---: | ---: | ---: |
| Shared `default` selection | 130.19 | 98.50 | 1.322x |
| Shared `hw:CARD=2,DEV=1` selection | 428.58 | 338.15 | 1.267x |
| Exclusive `hw:CARD=2,DEV=1` selection | 128.28 | 106.37 | 1.206x |
| Exclusive `plughw:CARD=2,DEV=1` selection | 257.67 | 99.77 | 2.583x |
| Playback timing, 48 kHz | 434.59 | 406.62 | 1.069x |
| Playback timing, 44.1 kHz | 433.86 | 407.08 | 1.066x |
| Playback timing, 96 kHz | 433.99 | 407.25 | 1.066x |

Selection includes constructing and dropping the owned input and returned ID;
it excludes opening a PCM. Timing measures the full `playback_status_timing`
function, with real null-PCM status and clock queries and a fixture-controlled
240-frame queue. Its before binary already contains changes 1 and 2, isolating
change 3. Timing instructions fall from approximately 762 to 750 per query;
both variants allocate zero Rust objects per query.

| Operation | Rust allocations | Reallocations | Requested bytes |
| --- | ---: | ---: | ---: |
| Shared alias | 2 → 1 | 0 → 0 | 14 → 7 |
| Shared hardware | 2 → 1 | 1 → 1 | 57 → 45 |
| Exclusive hardware | 2 → 1 | 0 → 0 | 30 → 15 |
| Exclusive plughw | 2 → 1 | 1 → 0 | 40 → 19 |
| Enumerate eight devices | 58 → 41 | 9 → 9 | 2,990 → 2,390 |

Enumeration's reliable benefit is 29.3% fewer Rust allocations and 20.1% fewer
requested bytes. Instructions decrease from 451,377 to 448,731 per scan. Median
cycles are 255,693 → 254,337 in confirmation, versus 268,275 → 261,796 in the
first comparison; variation prevents claiming a reliable cycle improvement.

`perf stat` records userspace hardware cycles/instructions and task-clock for
the entire test process, including startup, preparation, warmup and reporting.
Loop wall time is recorded separately. Each batch performs 2 million selections,
20,000 enumerations, 1 million timing queries or 40 million arithmetic controls.
Allocation counts cover one warmed operation, including its drops. Timed
allocator counter increments are disabled, but its enabled-state check remains.
Counts cover Rust's allocator, excluding libasound/libc allocations; requested
bytes sum allocation and reallocation requests, not retained/peak heap or RSS.

The enumeration preload fixture supplies two cards, four devices per card and
fixed capability boundaries. PCM opening, access/format/channel probes and
configuration use real libasound null PCMs. These are isolated backend
measurements, not hardware-driver latency or whole-game performance results.

## Rejected experiments and correctness

Ordinary constant division at 44.1/48 kHz regressed CPU throughput by 15–21%.
Explicit safe reciprocal products improved those two rates by 5.54–6.40x, but
regressed 96 kHz by 29% in cycles. Both implementations were removed. The
unchanged integer conversion remains; its confirmation controls vary about
1.5% for fixed rates and 2.1% for mixed rates between binaries.

Both the original source from `434ea4029` and the final source pass the same
five unit checks and thirteen fixture scenarios. These cover shared/exclusive
ID text, Unicode and embedded NUL suffixes, unchanged alias-error text, native
null-PCM stream shape, clock health, regular/empty inventories, unmatched
defaults, invalid device-name UTF-8 and failed probes. Timing scenarios cover
negative, zero, 240 and `u32::MAX` delays with successful and failed status
queries, checking delay arithmetic, timing quality and clock-health state.
An arithmetic-only test used for the rejected experiments was removed with
those experiments; measured archives preserve its original source and results.

Native Linux debug tests for ALSA, audio-core and platform pass 131 checks.
Scoped rustfmt, Clippy on all ALSA targets, Python compilation and the C fixture
with `-Wall -Wextra -Werror` pass. No physical output device or full application
render was exercised.

## Evidence and reproduction

[Provenance](2026-10-26-alsa-provenance.json) retains stage source patches,
compiler/build identities, dependency/configuration hashes, benchmark and
fixture source versions, correctness logs and all 443 measurements with dataset hashes.
[Original-source checks](2026-10-26-alsa-reference-checks.json) include the
independent reference compile command and scenario results. The provenance also
contains its verification script. Archived binaries and raw subprocess logs
remain locally under `target/alsa-performance`.

Every retained change had a baseline run before editing and an alternating
before/after comparison afterward. The individual datasets are
[owned IDs](2026-10-26-alsa-owned-pcm.tsv),
[enumeration](2026-10-26-alsa-direct-devices.tsv) and
[lazy fallback](2026-10-26-alsa-lazy-fallback.tsv). The final confirmations are
[selection/enumeration/controls](2026-10-26-alsa-final.tsv) and
[timing](2026-10-26-alsa-timing-confirm.tsv). Preliminary and rejected-candidate
measurements are also retained alongside them.

Run on Linux/WSL, with `perf`, a C compiler, pkg-config and the ALSA/platform
development libraries installed. Build each named stage before making its next
source edit; use fresh names for another experiment:

```sh
export CARGO_TARGET_DIR=/home/perfecttaste/deadsync-alsa-target
python3 scripts/benchmark_alsa.py --build my-before
# Apply one optimization.
python3 scripts/benchmark_alsa.py --build my-after
python3 scripts/benchmark_alsa.py --compare my-before my-after --fixture-stage my-after --runs 7 --output target/alsa-comparison.tsv
cargo test --locked -p deadlib-audio-backend-alsa -p deadlib-audio-core -p deadlib-platform
cargo clippy --locked -p deadlib-audio-backend-alsa --all-targets --no-deps
```

The runner tests five enumeration layouts and eight timing cases on every new
build. Timing workloads require both archives to contain the timing harness;
the earliest exploratory archives predate that addition.
