# Reuse callback dumps and combine native validation

Baseline: `7abdd1943f8e9b72774b8fe1d79b3a2d02af6f1b` (0.5.2363). Result: 0.5.2364. New executables were measured at 0.5.2363. Baseline executables are the preceding final normal-library binaries, built at 0.5.2362 with identical implementation/harness; its version bump was metadata only. Adjacent JSON contains source/binary hashes, raw CPU cycles, throughput, allocations/reallocations, requested bytes, retained payloads, authored traces, native end states and focused check receipts.

## Retained changes

1. A crate-private dump operation replaces a caller-owned Vec’s contents while retaining its allocation. BatchCompiler keeps a scratch Vec across function compilations instead of allocating/growing a fresh dump for every callback. The public Function::dump and program::dump APIs retain their owned output and byte format. The cache key and scratch buffer remain separate owned storage.

2. Generic compiled-program dumping checks the native-closure flag and writes the dump under one Lua lock. It no longer obtains and drops an unused environment table before taking the dump lock. Lua 5.1 functions always have table environments; their existing rooted Function already retains the environment. The compiler keeps the former environment probe’s assert_stack behavior. Native closures still produce the exact Unsupported native-closure error; ordinary Function::dump still returns empty bytes for them. Other Lua versions keep the existing checked/protected dump path.

3. BatchCompiler accepts borrowed bytes directly and reuses its last-successful bytecode Vec’s capacity on a miss. It removes the Cow wrapper and allocation of a replacement bytecode key for every distinct callback. Byte comparisons, numeric bits, object/cell/input identities and type contracts remain exact, and failures do not replace the last success.

All three mechanisms remain in deadlib-lua-legacy. Game callback schemas, ordering, retry policy, noteskin behavior and theme presentation are unchanged. The existing dump writer is reused; its unsafe pointer conversion now borrows a caller-owned Vec exclusively for the synchronous lua_dump call. StackGuard restores the caller’s top, the Function stays rooted under the lock, and lua_dump does not retain the pointer. No Game-side unsafe access was added.

This pass improves compilation of existing VM-free inputs, explicit scalar/byte state, actor actions and updates. It does not expand the accepted authored language or remove Lua from the default Scene.

## Measurement

Release, locked dependencies, LTO disabled, two build jobs, logical CPU 2 affinity. Timing processes run serially, outside compilation. GlobalAlloc covers Rust allocation requests across process threads, including mlua where routed through it; native malloc is excluded. Requested bytes are cumulative allocation/reallocation requests rather than peak retained memory.

Each of six authored fixtures uses three alternating process pairs for every individual and combined comparison. Ten native samples discard the first; each has 393,216 real input/update pairs, or 49,152 for both 16-callback fanouts. Every process first compares 96 authored Lua/native input and update steps, drops the original Scene/artifact, compiles with a separately finalized VM, proves its destruction, replays the authored trace, then times only the detached native owner. All handling digests, scalar bits, ordered actions and full native end states match. Preparation uses ten batches of 128, discarding the first.

The first buffer-reuse step reduced numeric fanout preparation cycles about 18%, allocations 82→68, reallocations 88→13 and requested bytes 45,468→23,892. Combining the check and dump then reduced numeric fanout preparation cycles another 9% in its individual comparison. Neither step changes native runtime representation.

Reusing bytecode key capacity removes seven allocations/4,438 requested bytes for eight distinct bindings and fifteen allocations/9,525 requested bytes for sixteen. The initial eight-callback timing was +17.5%; a reversed-first repeat measured −1.3% at both sizes, with identical allocation savings. Both data sets are retained rather than treating one timing result as conclusive.

## Validation and limits

61 focused checks passed: SDK program tests; actor and compiled input tests; method semantics/names; production OpenGL differential; and one focused Function::dump test each on Lua 5.1 and Lua 5.5. The dump test covers debug/stripped chunks and native closures, with exact stack-top comparisons under the owning Lua lock after repeated success and native-rejection paths. New batch regression alternates large binary and small numeric function dumps, compares dump bytes exactly, checks native errors and hostile environment metatables, and verifies results after compiler/cache/VM destruction. Existing tests cover bit patterns, cell identity/aliasing, byte state, malformed chunks, nil registers, receiver identity, errors, scheduling and fallback.

The render differential compares 240 RenderFrame structures and 240 pixel buffers across eight authored fixtures. Six ordinary Scene fixtures compare six update/input/draw frames each. All 144 long native processes prove loading VM finalization and compare authored traces plus full native end states. Another 72 preparation sensitivity processes verify authored behavior and VM destruction. Inputs remain runtime data; no action timeline is precomputed.

The default Scene still retains Lua. General loops/calls, queued/effect-owned behavior and other unsupported cases retain existing fallback. A batch retains its largest scratch/key buffer capacities until dropped; Game batches exist only during each compilation attempt. This trades bounded loading-time storage for fewer allocation/growth operations and does not change retained gameplay memory. Full Song --lib/full suite, the historical six-failure audit and a cross-theme matrix were not run.
