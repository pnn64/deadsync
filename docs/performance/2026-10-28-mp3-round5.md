# MP3 decoder: fifth optimization pass

This pass retains three safe stereo optimizations: stop boundary searches at
the last nonzero band, process intensity and mid/side bands directly, and reuse
runtime-computed MPEG-1 pan gains. The baseline is `9ad700d7c`. Every stage
matches the exact-output fingerprint; no public API or PCM arithmetic changes,
production unsafe code or heap allocations are introduced.

## Measurement method

Resident-input probes use the fixed Cargo build/package path, repository
release/bench profiles, a pinned Windows thread and `QueryThreadCycleTime`.
Seven process runs rotate four saved builds; each process reports eleven
measured-batch medians after warmup. CPU cycles, nanoseconds, allocation
counters, dispersion and source/fixture/binary/compiler/configuration hashes
are retained in [raw observations](2026-10-28-mp3-round5.tsv) and
[manifests and summary](2026-10-28-mp3-round5.json).

Twelve additional probes cover long, pure-short and 8 kHz mixed stereo shapes,
modes 1 and 3, and zero/sparse right spectra. Each stereo operation includes
restoring both source planes before calling the production kernel. The same
ten whole-file probes remain. All six measured allocation counters are zero
in **1,680 hot observations** and all 84 fresh-process observations across
two first-use comparisons.

The stages are `round5-cold-base`, `reverse-bands-current`, `fused-stereo`,
and `cached-intensity`. The following tables isolate each incremental change.

## 1. Search backward to the last nonzero band

Intensity eligibility needs only the highest nonzero band in each region.
Long bands now scan backward and stop at the first hit. Short windows each
perform the same search independently. This removes work below an already
established boundary and preserves the mixed-block rule that a nonzero short
region disables long-band intensity. All-zero regions still require a full
search.

| Input | Before cycles/op | After cycles/op | Reduction | CPU throughput |
| --- | ---: | ---: | ---: | ---: |
| Dense right, intensity only | 588.26 | 305.48 | 48.1% | 1.926x |
| Dense right, combined stereo | 2,509.70 | 2,178.41 | 13.2% | 1.152x |
| Sparse right, long intensity | 1,785.92 | 1,656.04 | 7.3% | 1.078x |
| Zero right, long combined | 7,592.20 | 8,361.83 | -10.1% | 0.908x |

The dense boundary-search gain is clear. The all-zero long combined case is
10.1% slower, and the reverse-search build has slower whole-file medians on
all ten inputs in this run. This change has a targeted benefit; the data do
not establish a general decoder gain from reverse searching alone.

## 2. Apply the selected transform directly by band

After determining all right-channel boundaries, each long or short-window
band receives intensity stereo or mid/side directly. This removes the
576-entry coupling bitmap, its writes, and the final full-spectrum flag scan.
Contiguous long-band slices also expose packed-f64 work to the compiler.
Mixed-block low bands are covered even when short-region data disables their
intensity eligibility. Top-band inheritance, invalid-pan handling and the
mid/side-only fast path retain their original equations and checks.

| Input | Before cycles/op | After cycles/op | Reduction | CPU throughput |
| --- | ---: | ---: | ---: | ---: |
| Dense right, combined stereo | 2,178.41 | 1,149.78 | 47.2% | 1.895x |
| Zero right, long combined | 8,361.83 | 3,861.99 | 53.8% | 2.165x |
| Zero right, pure-short combined | 7,502.55 | 6,243.22 | 16.8% | 1.202x |
| Zero right, 8 kHz mixed combined | 5,436.55 | 3,786.27 | 30.4% | 1.436x |
| Dense right, intensity only | 305.48 | 442.73 | -44.9% | 0.690x |

The last row is a counterexample: dense mode-1 processing is slower than the
reverse-only build. The final combined build remains faster than the original
baseline on that probe. Generated code confirms that the standalone stereo
function's stack reservation falls from **872 to 280 bytes** with direct band
processing, then to **216 bytes** with the gain cache. Its static instruction
count changes from 870 to 731 to 744. These counts cover the standalone body;
initializer/helper code is excluded, and they are not retired-instruction
measurements. Packed-f64 operations remain in the generated band loops.
[Assembly hashes, count method and cache layout](2026-10-28-mp3-stereo-codegen.json).

## 3. Reuse the five nontrivial MPEG-1 pan gains

A lazy immutable array computes positions 1-5 with the same runtime tangent,
division and expression order as uncached calls. `black_box` preserves the
runtime math path. Repeated band positions load two gains instead of calling
`tan` and repeating the divisions. Positions 0/6 and invalid positions retain
their direct paths, and LSF gain arithmetic is unchanged.

| Input | Before cycles/op | After cycles/op | Reduction | CPU throughput |
| --- | ---: | ---: | ---: | ---: |
| Zero right, long combined, pan 3 | 3,861.99 | 2,025.48 | 47.6% | 1.907x |
| Zero right, pure-short combined, pan 3 | 6,243.22 | 3,449.03 | 44.8% | 1.810x |
| LSF zero-right mixed control | 3,786.27 | 4,035.92 | -6.6% | 0.938x |

The LSF control becomes 6.6% slower despite unchanged LSF gain arithmetic.
Other untouched controls also move between binaries. The evidence supports
large gains for the repeated MPEG-1 pan calculations; a broad LSF speedup is
not inferred from this comparison. The measured lazy-lock object is **88
bytes, aligned to 8 bytes**, including its 80 bytes of numeric data.

## First-use pan-gain cost

The gain cache holds five f64 pairs: 80 bytes of numeric data plus lazy-lock
state. Initialization uses runtime `tan` with the original expression order;
`black_box` prevents compile-time substitution of differently rounded values.
Positions 0 and 6 retain direct constants, invalid positions retain `None`,
and LSF gains are unchanged. Only a valid MPEG-1 position 1-5 initializes the
cache; there is no heap allocation or production unsafe code.

Twenty-one fresh processes per stage alternate a first stereo call with zero
right input and MPEG-1 pan 3 across all long bands. Process launch, input setup,
thread pinning and allocation-TLS/cycle-query priming are excluded. Timing
includes the common Instant/counter wrapper shown in the saved probe.

| Stage | Median CPU cycles | MAD cycles | Median ns |
| --- | ---: | ---: | ---: |
| fused-stereo | 38,413 | 1,098 | 11,000 |
| cached-intensity | 43,461 | 1,097 | 13,100 |

The cached build adds 5,048 median CPU cycles in this first-use scenario.
This is one measured initialization case, not a universal first-call cost.
All measured allocation counters are zero.

## Whole-file results and limitations

All columns below are CPU cycles per complete resident-file decode, including
reset. Final ratios compare the two saved builds directly.

| File | Original | Reverse | Direct bands | Cached final | Final reduction |
| --- | ---: | ---: | ---: | ---: | ---: |
| LAME 44.1 kHz stereo | 23,888,734 | 26,470,712 | 24,641,180 | 25,426,551 | -6.4% |
| Shine 44.1 kHz stereo | 25,240,743 | 26,478,505 | 26,097,344 | 24,276,919 | 3.8% |
| Media Foundation 44.1 kHz stereo | 25,095,434 | 27,179,916 | 26,188,216 | 24,297,442 | 3.2% |
| Media Foundation 8 kHz stereo, short fixture | 62,009 | 68,374 | 67,167 | 65,630 | -5.8% |
| 44.1 kHz stereo VBR | 29,633,048 | 30,236,344 | 29,735,995 | 28,006,884 | 5.5% |
| 8 kHz stereo CBR | 5,388,176 | 5,713,476 | 5,684,721 | 5,243,087 | 2.7% |
| Synthetic long intensity | 30,621,348 | 32,024,611 | 32,060,938 | 29,706,362 | 3.0% |
| Synthetic short intensity | 29,253,095 | 31,390,916 | 31,216,192 | 29,095,274 | 0.5% |
| Protected 44.1 kHz stereo | 24,222,264 | 25,407,783 | 25,650,441 | 24,398,852 | -0.7% |
| Protected 22.05 kHz mono | 8,310,270 | 8,788,450 | 8,496,188 | 8,483,016 | -2.1% |

Six final file medians improve and four regress. Final changes range from
5.5% fewer cycles to 6.4% more cycles. These mixed estimates and the movement
of unchanged controls do not establish a uniform end-to-end speedup. The
retained gains are strongest in the targeted stereo kernels. The pure-mid/side
control changes from 1,067.91 to 856.53 cycles despite unchanged arithmetic;
compiler, stack/layout and run variation contribute to the measured results.
All medians, ranges and MADs are retained in the linked JSON.

A [PE-data audit](2026-10-28-mp3-matrix-layout.json) records the cosine table
addresses: both complete SYNTHESIS and IMDCT_LONG matrices are 16-byte aligned
in all four binaries. Other sources of the control shifts remain unresolved.

## Correctness

All 58 integration tests and all-target Clippy with warnings denied pass.
Scoped rustfmt and `git diff --check` pass. The new boundary test independently
constructs 216 combinations of sample
rate, block shape, mode and valid/invalid pan. It compares every output f64
bit, including signed zero and subnormal inputs, and passed before and after
removing the coupling flags. A second test compares all five cached MPEG-1
gain pairs against runtime tangent equations, repeatedly, including signed
zeros, subnormals, maximum finite values and infinity.

[Source/probe/profile audit](2026-10-28-mp3-round5-source-audit.json).

Original, reverse-search, direct-band and cached builds produce identical
output for **80 files**: 42 encoder files, 36 CBR/VBR seek files and two protected
files. All **315,886,528 emitted bytes**, including the prior DSP, bounded-field,
spectral, stereo and exhaustive CRC probes, have SHA-256
`f0181df4f22ed43a0748c588ab4f3d0faa3c3b4ea94ea2c81fb90ed5e095ae76`.
