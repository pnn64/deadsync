Software-renderer YUV420 uploads now select a hardware FMA path once per upload on supported x86/x86-64 CPUs. It batches the four pixels sharing each chroma pair, preserves fused arithmetic and byte-rounding order, and uses explicit bounds and NaN handling before an unchecked byte conversion. The original scalar pixel loop remains the portable fallback. The batch choice is a const parameter, so there is no per-pixel feature dispatch. No inline assembly, architecture intrinsics, dependency or allocation is added.

The complete public `update_yuv420_texture` benchmark improves **1.776x at 1080p**, about **43.7% less CPU cost**, with six paired ratios from **1.691x to 1.812x**. Independent median wall times are **20.40 ms before to 11.48 ms after**. At 720p the improvement is **1.785x**, from **9.09 ms to 5.11 ms**. These are CPU texture-upload measurements for the software renderer, not hardware video decoding, GPU rendering or whole-game frame time.

The baseline is `03b142ad3`. The same committed `yuv_performance` example was built and archived before and after applying the production change. It calls the real public software-renderer API without creating a window. The release profile is unchanged: opt-level 3, fat LTO, panic abort, generic x86-64 CPU and static CRT. Six process pairs alternate executable order and rotate fixture order with arguments `0, 3, 6, 9, 12, 15`. Each process pins its thread to logical CPU 2 and records ten rounds, excluding only the first as warmup. All other rounds and outliers remain in the CSVs.

CPU cycles use `QueryThreadCycleTime`; wall time uses `Instant`. Fixture creation and allocation are outside timing. Validation, normalization-table preparation, pixel conversion, output stores and texture metadata updates are inside the public call. Input planes vary across pixels and repeat between timed calls. Each round runs `(2_000_000 / pixels).clamp(2, 30000)` iterations. All cases assert zero allocation/reallocation/free churn for the retained texture update. Cycle columns are independent medians of process medians; speedups are medians of paired process ratios, so their quotient can differ. No builds or tests from this change overlapped timing.

Host: Intel Xeon E5-2696 v4, Windows x86-64, rustc 1.99.1 / LLVM 23.1.1. Disassembly of the exact measured executables confirms repeated scalar `fmaf` calls in the original pixel loop. The new hardware path uses packed `vfmadd...ps` arithmetic and `vcvttpd2dq` conversions, while the original calls remain available in the portable path. Arithmetic stays in f32 through the product by 255, then widens to f64 before adding the half bias, preserving boundary rounding. Clamping and NaN substitution guarantee finite values in [0, 255] before the unchecked cast. The target-feature call is guarded by runtime CPU detection.

The new regular tests compare both batch arithmetic and runtime-selected uploads with the portable loop across 4,608 combinations of dimensions, plane/output offsets and float parameters. They include lookup-table thresholds and output guard bytes. Image creation, resizing, retained storage, and invalid planes are checked separately; invalid updates preserve both the current image and its storage. The existing scalar-rounding reference test now also checks batches at half-byte boundaries, signed zeros, subnormals, infinities, NaN payloads and one million random float inputs. The opt-in exhaustive test covers all 16,777,216 Y/U/V byte triples for three coefficient sets (BT.601, BT.709, BT.2020), each with full and limited range: 100,663,296 color cases for each tested path.
