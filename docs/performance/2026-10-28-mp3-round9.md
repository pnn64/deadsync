# MP3 decoder: ninth optimization pass

The MP3 production baseline is `79ba7b9f9`. This pass retains two CPU
optimizations and one storage simplification: avoid repeated right-channel DSP
resets during mono runs, bypass requantization for entirely zero coefficients,
and keep one scalefactor array across a frame's granules. All use safe Rust and
preserve the public API. The scalefactor change's clearest benefit is a smaller
generated stack frame; its CPU results are small and mixed.

## Measurement method

The final stages are `round9-final-base`, `round9-active`, `round9-zero`, and
`round9-final`, in that order. Each builds through the same fixed Cargo path,
compiler, repository bench profile and configuration. Saved executables and
source/fixture hashes are checked before comparison. Seven fresh processes per
stage rotate their order. Each process reports the median of eleven measured
batches after warmup, on Windows logical CPU 2 using `QueryThreadCycleTime`.
Capture-time initial samples are excluded from decisions. Compilation and
correctness checks run outside the decision timings.

There are **154 workloads and 4,312 observations** in the
[raw data](2026-10-28-mp3-round9.tsv) and
[manifests, medians, ranges and MAD](2026-10-28-mp3-round9.json). In addition to prior kernel
probes, this pass adds six steady empty-frame cases, three mono file fixtures,
and nine zero/first-nonzero/last-nonzero requantization cases. Empty-frame probes
decode on a persistent decoder; setup and packet construction are untimed.
Each requantization operation processes one 576-coefficient granule. CPU
throughput below is the inverse cycle ratio. Nanosecond measurements remain in
the raw data.

All six heap counters are zero in all 4,312 final observations, and all 4,060
initial-screen observations. There is **no heap-allocation reduction** in this
pass. The raw data retains large process outliers; no samples are discarded.
Small differences should be read alongside the recorded dispersion.

## 1. Reset right-channel DSP only after it was used

Every successful mono frame previously reset 4,608 bytes of hybrid history and
8,192 bytes of synthesis history in the unused channel, including consecutive
mono frames. A private boolean records whether the right DSP has been touched
since its last reset. Stereo decoding and stereo draining mark it; the next
mono frame clears the right history and flag. Global DSP reset clears the flag.
Thus steady mono avoids **12,800 bytes of history clearing per frame**, while
stereo-to-mono transitions keep the same history and ring-offset behavior.

| Input | Before cycles | After cycles | Reduction | CPU throughput |
| --- | ---: | ---: | ---: | ---: |
| MPEG-1, mono empty frame | 12,830.47 | 11,023.01 | 14.1% | 1.164x |
| MPEG-2, mono empty frame | 7,049.73 | 5,288.57 | 25.0% | 1.333x |
| MPEG-2.5, mono empty frame | 7,068.59 | 5,252.57 | 25.7% | 1.346x |

The boolean fits existing padding with this compiler and target:
`FrameDecoder` stays **51,568 bytes, alignment 16** at every stage. `Synthesis`
stays 8,208 bytes, alignment 16. This is a measured target-specific layout,
not a cross-platform size guarantee.

## 2. Skip amplitude calculation and reordering for zero coefficients

After the existing shape check, lazy power-cache access and output clear,
bitwise OR reduces all 576 i16 coefficients. The reduction is zero exactly when
every coefficient is zero, including the full signed-i16 domain. That case
returns the already-cleared positive-zero spectrum, avoiding all gain,
per-band amplitude, coefficient and reorder work. `power(0, scale)` already
returns positive zero for every scale. Hybrid and synthesis continue processing
their overlap and filter tails.

The cache is still initialized on the same first call, including zero input.
The invalid-shape error still occurs before initialization or output mutation.
The compiler emits packed integer `por` operations for the safe reduction.

| Input | Before cycles | After cycles | Reduction | CPU throughput |
| --- | ---: | ---: | ---: | ---: |
| Long, all zero | 1,535.18 | 309.93 | 79.8% | 4.953x |
| Pure short, all zero | 2,909.69 | 297.42 | 89.8% | 9.783x |
| Mixed, all zero | 2,783.04 | 309.93 | 88.9% | 8.980x |

This guard has costs on nonzero input; retain these counterexamples:

| Input | Before cycles | After cycles | Reduction | CPU throughput |
| --- | ---: | ---: | ---: | ---: |
| Long, common coefficients | 3,043.81 | 2,706.87 | 11.1% | 1.124x |
| Long, wide coefficients | 36,324.40 | 36,453.24 | -0.4% | 0.996x |
| Long, only first coefficient nonzero | 1,543.09 | 1,605.20 | -4.0% | 0.961x |
| Long, only last coefficient nonzero | 1,513.89 | 1,735.37 | -14.6% | 0.872x |
| Mixed, common coefficients | 3,601.12 | 3,751.26 | -4.2% | 0.960x |

The largest listed guard cost is 14.6% for a long block with only its final
coefficient nonzero. The final combined median for that probe is 1,611.57
cycles, versus 1,597.30 at baseline; code layout and run variation contribute
to the stage-to-stage differences. This is a targeted zero-granule improvement,
not a claim that all spectra become faster.

The standalone requantization body grows from 501 to 652 static instructions;
its stack reservation stays 264 bytes. These are generated-code counts,
not retired instructions or whole-program code-size measurements.

## 3. Keep the current scalefactors as the next granule's predecessor

The frame loop previously built a fresh two-channel factors array per granule,
then moved both entries through `mem::take` into a separate
`[Option<ScaleFactors>; 2]`, even after the final granule. One array now lives
outside the granule loop. Granule zero passes no predecessor; granule one reads
its channel's existing factors before replacing that entry. This removes the
separate previous-factors array and the two end-of-granule move/reset operations.

The generated standalone `FrameDecoder::decode` stack reservation falls from
**1528 to 1240 bytes (288 bytes, 18.8%)**.
Its static instruction count falls from 3,073 to 3,066. These figures exclude
callee stack use and instructions. Both `ScaleFactors` and its Option measure
136 bytes here; no discriminant-size reduction is claimed.

| Input | Before cycles | After cycles | Reduction | CPU throughput |
| --- | ---: | ---: | ---: | ---: |
| MPEG-1, mono empty frame | 8,032.33 | 8,166.09 | -1.7% | 0.984x |
| MPEG-2, stereo empty frame | 8,392.45 | 8,215.82 | 2.1% | 1.021x |
| MPEG-2.5, mono empty frame | 4,055.61 | 3,930.42 | 3.1% | 1.032x |
| MPEG-2.5, stereo empty frame | 8,246.68 | 8,142.07 | 1.3% | 1.013x |

These small CPU changes are mixed. MPEG-1 empty mono regresses 1.7%, while
MPEG-2.5 empty mono improves 3.1%. The change is retained for removing the
intermediate storage and reducing the generated stack reservation; no broad
throughput improvement is attributed to it.
[Assembly counts, calls, layout probes and commands](2026-10-28-mp3-round9-codegen.json).

## Rejected clear removal

The initial screen removed the unconditional requantization output clear,
because all valid band layouts overwrite the destination. Exact outputs passed,
but common long-block requantization rose from 3,062.46 to 3,399.62 cycles
(11.0% worse). The generated body lost five static instructions but increased
its stack reservation from 264 to 328 bytes. That one-line removal is rejected;
the production output clear remains. The zero shortcut is a separate replacement.

The initial screen used 145 workloads and the earlier verifier trace. Its four
stages must not be combined with final-stage timings:
[raw screen](2026-10-28-mp3-round9-screen.tsv),

## Exact behavior and checks

All **68 tests**, strict all-target Clippy, scoped formatting and whitespace
checks pass. No unsafe code is added. The two new integration oracles compare
mono/stereo transitions against independent mono histories in all three MPEG
versions, and compare all sixteen SCFSI reuse masks against explicitly encoded
factors for both channel counts across repeated frames.

The verifier now poisons requantization destinations with distinct quiet NaNs
and checks both varied full-domain coefficients and all-zero input at all nine
rates, five shapes and 256 gain values: **23,040 output vectors**. It also
replays coded stereo/empty mono transitions and repeated empty frames in each
version/channel configuration, alongside the existing bounded-bitstream,
Huffman, CRC, scalefactor, stereo, hybrid and synthesis traces.

All four stages produce the same **399,704,972-byte** trace across
**80 files** (42 encoder fixtures, 36 seek fixtures and two protected
CRC fixtures), with SHA-256:

`c0590a0b08cb9f591486242abc6b5d8d09d54d7f4a7fb90fdcb3b7473d1f1458`

The selected 13-file trace is 374,936,972 bytes with SHA-256
`fe6e29063c778416ff45379ee00d543e79a652a34ffeddd1f146f27c3e0d1ee0`.
These traces include kernel/error observations as well as PCM. Their expanded
coverage changes both size and hash from earlier passes.
