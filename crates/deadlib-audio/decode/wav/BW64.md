# BW64 size mechanics and compatibility boundaries

[ITU-R BS.2088-2 (2025), Annex 1 section 4.2](https://www.itu.int/dms_pubrec/itu-r/rec/bs/R-REC-BS.2088-2-202511-I!!PDF-E.pdf)
defines dummyLow/dummyHigh at the position used by RF64 sampleCount. BW64 readers
ignore them and writers emit zero. Its current profile does not use fact.
This differs from the RF64 fact-sentinel rule in EBU Tech 3306.

The crate now keeps that distinction throughout borrowed, seekable and forward
decoding, generic muxing, and both writer finalization paths. All BW64 output
zeros bytes 36..44. Ds64.sample_count and reader ds64_sample_count accessors
still expose the original raw words for inspection and exact container copying;
they never supply a BW64 decoder duration. A fact value of 0xFFFFFFFF in a
compatibility file remains the literal u32 value rather than selecting dummy
words. RF64 retains its sentinel behavior and existing no-fact fallback.

Ordinary contiguous PCM counts come from the physical data extent and can exceed
u32 without using fact or dummy words. The crate continues to accept and emit
BW64 float, ADPCM and wavl as explicitly scoped compatibility extensions. A
writer requiring fact rejects counts above u32::MAX: known-length construction
fails before header I/O, and generic incremental/wavl count checks fail before
the oversized record is written. A count exactly equal to u32::MAX is representable.
RF64 supports the larger fact counts. BW64 compressed/segmented examples and
float/extensible output do not establish conformance to a normative BW64 profile.
ADM requirements, profile validation and semantic interpretation remain open.
